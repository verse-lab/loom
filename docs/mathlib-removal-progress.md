The first implementation increment reduces imports and prepares standalone
control foundations. It is committed as `0dc0ce1`. The second increment adds
the standalone assertion-order hierarchy. Full mathlib removal remains in progress.

Implemented changes:

- Added a repeatable compiled-dependency audit in `scripts/AuditDependencies.lean`.
- Added a Lake test driver with extraction regression fixtures. The initial
  result-order, duplicate, logging, and branching checks passed on the original
  implementation before the trim. Further checks cover retained join-point
  lets, divergence logs, and helper behavior.
- Moved the `FinEnum` candidate instance into `LoomMathlib.Candidates`, in a
  separate local integration package. Its tests check automatic synthesis,
  predicate filtering, empty results, and enumeration order.
- Removed unused tree/function imports and the explicit mathlib tactic/helper
  imports; replaced all 41 `introv` uses with core introductions.
- Added a standalone list congruence lemma and used explicit monoid laws in
  proofs that had depended on transitively imported instances.
- Replaced extraction's target and application-argument helpers with Lean APIs,
  preserving target lets and providing an explicit out-of-bounds contract.
- Added namespaced `Loom.ContT`, `Loom.WriterT`, and `Loom.LogMonoid`, their laws,
  and explicit mathlib conversions. These compile without external packages
  and coexist with mathlib. They are not yet wired into the WP semantics.
- Added a native-consumer fixture and CI checks for the standalone
  foundations and optional adapter.

The compiled audit of `import Loom` went from 440 to 222 mathlib modules.
Direct references to mathlib declarations went from 229 to 224. This illustrates
that the trim mostly removes transitive imports: the order-theory work remains.
The root manifest still requires mathlib and its packages. These figures are
import counts, not build-time measurements.

Consumers supplying `Candidates` directly retain that interface. Consumers
relying on automatic `FinEnum` candidates must add the local integration package
and import `LoomMathlib.Candidates`; see its README. The integration's manifest
is generated by Lake and pins the same mathlib commit as the root checkout.

The second increment adds:

- `Loom.Order.Preorder` and `PartialOrder`, owning their relation, with scoped
  `⊑ₗ` notation. Top/bottom structures refer to that preorder rather than
  introducing another relation. Binary operations use scoped `⊓ₗ` and `⊔ₗ`.
- Lattices, complete lattices, Boolean algebras, and complete Boolean algebras.
  Shared parent operations are definitionally equal, with regression checks
  for the lattice, top, and bottom inheritance paths.
- Predicate-defined arbitrary bounds and range-based `iInf`/`iSup` for
  arbitrary index sorts and universes, including proposition indices.
  Introduction/elimination, monotonicity, congruence, dependent double bounds,
  exchange, and empty/constant cases are proved.
- Boolean implication's adjunction, complement laws, De Morgan laws, and
  finite-meet/arbitrary-join distribution with its dual. Distribution is
  proved from Boolean laws and completeness; no atomicity or stronger
  complete-distributivity assumption is added.
- `Prop` and dependent-function instances; the function domain may be any
  `Type` universe. Logical implication, finite lattice operations, and
  pointwise entailment reduce directly. Indexed operations normalize via
  proved simplification lemmas. `Id` and continuation bridges retain
  preorder-only, Boolean-only, and complete-lattice assumption levels.
- A three-element chain model, including a proof that its middle element
  has no complement, plus nested/dependent predicate and universe tests.
- Explicit mathlib conversions at the preorder, lattice, complete-lattice,
  Boolean, and complete-Boolean levels. Generic compatibility checks preserve
  mathlib's operations, including indexed bounds, by definitional equality.
  Mixed files use `open scoped Loom.Order` and qualified operation names;
  importing the adapter installs no global conversion instances.

The existing semantics still use mathlib. The new foundation is imported through
`Loom.Order.Instances` or `Loom.Order.Control`; it is not yet re-exported by
`import Loom`. Consequently this increment does not further reduce that root
module's mathlib import count. The full source library and static target include
the new modules through the existing Lake globs.

Next come the `MonadUtil`/`SpecMonad` migration, use of the standalone controls
in semantics, the algebra and WP/WLP proof ports, and the Veil migration.
The foundation's lemma surface can grow as those proof ports expose additional
requirements. Full Veil validation, Git distribution of the adapter, fresh
mathlib-free builds of the entire library, and performance comparison remain
outstanding. The audit and focused regression tests are a starting baseline;
they do not constitute completion of every baseline task in the full plan.

Validation commands:

For the second increment, `lake test`, `check_foundations.py`,
`lake build Loom:static`, and the integration test suite passed. The native
executable check passed in the first increment; it does not yet exercise the
new order foundation through migrated semantics.

```bash
lake build
lake build Loom:static
lake test
python3 scripts/check_foundations.py
lake -d integrations/mathlib test
lake -d tests/native exe smoke
lake env lean --run scripts/AuditDependencies.lean /tmp/loom-audit
```

`check_foundations.py` replaces `LEAN_PATH` with only this checkout's build
directory. Thus the control and metaprogramming tests cannot obtain imports
from cached external packages. This now includes the order models and laws.
The native fixture builds an executable and
executes an extracted computation. A separate attempt with
`precompileModules := true` was stopped because Lake started building mathlib's
entire shared library. That configuration remains to be validated after the
standalone semantics port; it is not enabled in this increment's CI.
